# Инженерный процесс RentalDesk

**Статус: ПРИНЯТО.** Проект разрабатывается как реальная коммерческая система, при этом обучение и самостоятельная реализация PHP являются приоритетом.

## Распределение ответственности

**Пользователь — backend-разработчик:** самостоятельно проектирует и пишет PHP/Symfony-код, миграции, бизнес-логику, тесты критичных операций. Может запрашивать теорию, подсказки, пошаговый разбор API или code review. Не подменять самостоятельную работу готовым кодом без прямой просьбы.

**Ассистент — наставник, архитектор-ревьюер и frontend-разработчик:** ставит осмысленные тикеты, помогает делать trade-off-анализ, ревьюит PHP-код, объясняет неизвестные механизмы, самостоятельно разрабатывает Vue/TypeScript frontend; согласует контракты с backend и тестирует интеграцию. Не утверждать, что браузер/production-сборка проверены, если фактически нет.

## Definition of Ready (до сложной реализации)

- Сформулирован бизнес-сценарий и смысл функции.
- Известны входы/выходы, HTTP-контракт, статусные коды и основные негативные сценарии.
- Названы инварианты и источник истины.
- Для нетривиальных решений описаны альтернативы, trade-offs и при необходимости ADR.
- Понятна транзакционная граница и риски гонок.
- Тикет соответствует текущему этапу и не ломает готовые функции.

## Цикл работы

1. Тикет целиком: цель, критерии готовности, 2–5 основных проверок.
2. Проектирование: доменные связи, инварианты, данные, API, транзакции.
3. Отдельная Git-ветка `feature/...`, `fix/...` или `chore/...`.
4. Пользователь самостоятельно пишет backend; ассистент не выдаёт решение до попытки, если не попросили.
5. Code review: корректность, читаемость, безопасность, Doctrine/SQL, конкурентность, тестируемость.
6. Проверка: миграции, `php -l`, целевые PHPUnit-тесты и интеграционные тесты, реальные `curl`/HTTP. Статический анализ и CI вводим по мере настройки.
7. Ассистент обновляет frontend и проверяет API-интеграцию по реальным контрактам; желательно `npm run build`.
8. Обновляем `CURRENT_STATE.md`, ADR и API-контракты. Осмысленный коммит; слияние проверенной ветки в `main`.

**Нет** правила «обязательно писать тест на каждый getter/foreach». Тестировать в первую очередь инварианты, переходы состояния, деньги, транзакции, гонки, обработку ошибок, регрессии.

## Git

Два проекта сейчас в разных каталогах WSL. План — отдельные локальные репозитории. `main` должен соответствовать проверенной базе; незаконченные функции — в feature-ветках.

Рекомендуемые сообщения:

```text
chore: establish Symfony backend baseline
feat: introduce Asset domain model
feat: register asset via API
test: cover asset state transitions
fix: prevent conflicting reservations
docs: record asset inventory migration strategy
```

Первый backend commit ещё **не подтверждён** в истории диалога по состоянию 30.10.2026: были подготовлены файлы, исправлен `core.autocrlf=input`, добавлен `.gitattributes`, исключена `.idea`. У незавершённых `Asset`, `OrderItem`, `RentalOrder` и соответствующих репозиториев нужно проверить индекс, прежде чем коммитить стабильный baseline.

**Git-гигиена:**
- Игнорировать `vendor/`, `var/`, `.idea/`, `.env.local`, кэши, `node_modules/`, `dist/` для фронтенда.
- `.env` и `.env.dev` можно коммитить только без секретов; перед первым коммитом проверить `compose.yaml`.
- Окончания строк — LF в WSL; `.gitattributes` фиксирует правила для команды.
- Просматривать `git diff --cached --name-only`, `git diff --cached --check`, содержимое env-конфигураций.
- Git сам по себе не резервная копия; удалённый приватный репозиторий желателен позднее.

## API и фронтенд

- Контракт — согласованный ответ JSON и ошибки, а не «что вернулось случайно».
- Существующая версия GET: список в корневом JSON-массиве, без `data`.
- Автоматическое `MapRequestPayload` допускается и предпочтительно для простого HTTP DTO; проверить статус/формат ошибок валидатора на реальных запросах.
- Визуальные улучшения frontend не должны скрывать ошибку отправки; проверять submit, числовые поля, загрузку, ошибки и новый объект в каталоге.
- UI допускает временную функциональность только если она честно подписана как неактивная, без вымышленных данных.
- Стиль: тёмный графит / чёрный / оранжевый, **Graphite & Ember**; эволюция UX параллельно backend.

## Отношение к инструментам

Symfony Messenger, RabbitMQ, Redis, Kafka, Kubernetes, ClickHouse, микросервисы и т.п. — **не обязательны**. Вводить только по доказанной потребности и с пониманием стоимости эксплуатации. Идемпотентность/блокировки/внешние API освоить сначала на реальных кейсах RentalDesk.
