# ADR-0005: временное резервирование конкретных инструментов

- **Дата:** 30.10.2026.
- **Статус:** ОТКРЫТО / решение ещё НЕ принято.

## Контекст

`InventoryItem.stock - reserved` недостаточно, чтобы доказать доступность инструмента на конкретный интервал дат. Появляются параллельные брони, выдачи, возвраты и обслуживание.

## Зафиксированные требования

- Не допускать двойного бронирования одного физического экземпляра на пересекающиеся интервалы.
- Должна быть корректная реакция на два конкурентных запроса, сбой и повтор запроса.
- Решение должно опираться на гарантии PostgreSQL, а не только на `if` в PHP/Redis-lock.
- Создание черновика не должно само по себе резервировать инструменты.

## Обсудить до реализации

- Полуоткрытые периоды и timezone/UTC.
- Таблица броней/выдач и связь `OrderItem` ↔ `Asset`.
- `EXCLUDE USING gist` / конкурентный `UPDATE` / row-level locking — сравнить применимость.
- Статус удержания и сроки его действия, идемпотентность, повторная обработка.
- Транзакционная граница, порядок блокировки, deadlock/retry.
- Тест с несколькими конкурентными транзакциями в настоящем PostgreSQL.

## Вывод

Пока не начинать кодировать блокировки; сначала выбрать точный инвариант и сохранить конкретное решение отдельным ADR.
