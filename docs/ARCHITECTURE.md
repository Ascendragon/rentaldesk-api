# Архитектура RentalDesk

**Актуализировано:** 30.10.2026. Разделяет целевую архитектуру и текущую реализацию. Подробные решения — в `adr/`.

## 1. Принятый стек

- **Backend:** PHP 8.5, Symfony 7.4 LTS, REST JSON API.
- **БД:** PostgreSQL в Docker, миграции Doctrine.
- **Доступ к данным:** Doctrine ORM для сущностей/простого чтения и записи; Doctrine DBAL или явный SQL для сложных атомарных операций и точного контроля блокировок.
- **Frontend:** Vue 3 + TypeScript + Vite. Отдельная папка/репозиторий.
- **Окружение:** WSL/Linux; локальный PHP dev server на `127.0.0.1:8000`, Vite обычно на `5173` с proxy `/api`.
- **Архитектурный стиль:** модульный монолит; модули постепенно выделяются по ответственности, без преждевременной сети микросервисов.

Версии в этом документе — версии **текущего проекта на момент среза**, не универсальные обязательные версии навсегда.

## 2. Слои и границы

```text
HTTP Request
  → Symfony Controller           маршруты, статусы HTTP, представление ошибок
  → Request DTO + Validator      проверка структуры/формата ввода
  → Application Service          сценарий, транзакционная граница, координация
  → Domain Entity                инварианты, поведение, переходы состояний
  → Repository / ORM / DBAL      хранение и атомарные SQL-операции
  → PostgreSQL                   ограничения, уникальность, FK, транзакции

Domain / Response DTO → HTTP JSON → Vue API-client → UI
```

- Не помещать SQL, HTTP Request или EntityManager в доменную сущность.
- DTO запросов **не являются** сущностями БД.
- Response DTO формируют публичный контракт, не сериализовать ORM Entity вслепую.
- Валидация DTO дополняет, но не заменяет инварианты доменной модели и ограничения PostgreSQL.
- Репозитории, сервисы и абстракции вводить по назначению. Не создавать бессмысленные обёртки для каждого метода.

## 3. Доменная модель

### InventoryItem — модель/тип оборудования

**РЕАЛИЗОВАНО:** сущность `InventoryItem` с полями `id`, `name`, `stock`, `reserved` и методами `getAvailableUnits`, `canReserve`, `reserve`, `canRelease`, `release`; PostgreSQL содержит ограничения `stock >= 0`, `reserved >= 0 AND reserved <= stock`.

**Переходное состояние:** `stock` и `reserved` пока используются публичным API и фронтендом. Их нельзя удалять без переходной миграции.

### Asset — физический экземпляр

**ДОМЕННАЯ МОДЕЛЬ РЕАЛИЗОВАНА, HTTP API ЕЩЁ НЕТ.** `InventoryItem 1:N Asset`, каждый инструмент имеет собственный идентификатор, код, цену приобретения, дату приобретения и жизненный цикл. История ремонтов/аренд ещё не реализована.

Реализованные поля доменной модели:

| Поле | Тип/идея |
|---|---|
| `id` | генерируемый ключ |
| `inventoryItem` | обязательная ссылка на модель (`ManyToOne`) |
| `inventoryCode` | непустой уникальный код до 64 символов; уникальность в БД |
| `purchasePriceKopecks` | `?int >= 0` |
| `purchasedAt` | `?DateTimeImmutable` |
| `status` | PHP backed enum `AssetStatus`: `active`, `maintenance`, `retired` |

Статус `active` означает исправность/допуск к эксплуатации, **не** отсутствие аренды на даты. В домене есть переходы `active → maintenance → active`, а также `active/maintenance → retired`; восстановление `retired` запрещено. Эти правила покрыты 9 unit-тестами. Блокировки переходов при действующей аренде ещё требуют разработки. ORM round-trip на PostgreSQL проверен интеграционным тестом. Дополнительные DB `CHECK` для `status` и цены были согласованы для миграции, наличие всех ограничений следует дополнительно подтвердить SQL-инспекцией.

### Критический инвариант количества

**ПРИНЯТА ЦЕЛЬ:** после завершения перехода на поэкземплярный учёт `Asset` должен стать источником истины для физических экземпляров. **ОТКРЫТО:** точные правила вычисления агрегатного наличия, исключения `retired`/`maintenance`, временный dual-write, перенос текущих `stock`/`reserved`, поддержка агрегатного режима учёта.

Недопустимы два независимо редактируемых «истинных» значения `InventoryItem.stock` и `COUNT(Asset)`.

Перед миграцией: выбрать модель перехода; определить backfill существующих 4+ записей и `stock` штук на модель; проверить ограничения и согласованность; обновить API и фронтенд. Не проводить массовое изменение схемы без плана отката и проверки данных.

### RentalOrder и OrderItem

**ЧАСТЬ КОДА — ЧЕРНОВИК.** В старом standalone PHP прототипе существовали заказы и позиции; в Symfony созданы файлы Entity, но их модель, связи и миграции не утверждены как завершённые.

Целевая идея:

```text
RentalOrder 1 ─────── N OrderItem
OrderItem N ─────── 1 InventoryItem (либо выделенный вариант состава/Asset allocation)
```

Детали: `Collection` Doctrine для `OneToMany`, owning side у `ManyToOne`, синхронизация обеих сторон, проверка статуса заказа при изменении, расчёт цены по позиции. **ОТКРЫТО:** хранение дат, отдельная бронь vs заказ, назначение конкретного `Asset`, частичный возврат/выдача, состояния и идентичность позиции при разных сроках.

### Денежные значения

**ПРИНЯТО:** денежные суммы хранить целыми числами в **копейках**, не в `float`. Цена в `OrderItem` — **снимок тарифа** на момент создания/подтверждения, а не ссылка на меняющуюся текущую цену. Точный момент фиксации тарифа и стратегия валюты ещё должны быть утверждены до реализации заказов.

### Даты и конкурентность

**ПРИНЯТА цель:** бронирование зависит от временных интервалов и конкретных экземпляров, должно выдерживать конкурентные запросы.

**НЕ РЕШЕНО:** полуоткрытые интервалы `[start, end)`, UTC и отображение таймзон, конкретный SQL-механизм защиты от пересечений, идемпотентные ключи, модель hold/expiry, порядок блокировок, уровни изоляции. Это предмет отдельного ADR перед реализацией.

## 4. Базовые инварианты

- `InventoryItem`: непустое корректное имя; `stock >= 0`; `0 <= reserved <= stock`.
- `Asset`: уникальный код и допустимая цена; изменения состояния выполняются через доменные операции, не произвольный setter.
- Черновик заказа не резервирует склад самостоятельно; подтверждение/резервирование — отдельная атомарная бизнес-операция **(целевая схема, ещё не реализована)**.
- Публичные API создания не должны принимать произвольный `reserved`, статус или другие управляемые системой поля.
- Проверка существования свободного инструмента только в PHP **не гарантирует** отсутствие гонки; нужна атомарность на уровне БД.
- При удалении карточки нельзя неявно уничтожить юридически/финансово значимую историю.

## 5. Технические ограничения

- Проверять `CHECK`, `UNIQUE`, `NOT NULL`, внешние ключи на уровне БД; помнить, что ORM-атрибуты не всегда генерируют все нужные ограничения.
- Doctrine ORM может держать управляемую сущность в identity map; прямые DBAL UPDATE не синхронизируют объект автоматически. Не смешивать их без чёткого плана.
- Миграции после применения не переписывать задним числом; делать новые миграции.
- При развитии тестов делать акцент на интеграционных сценариях с PostgreSQL и моделировании сбоев.
